# Архитектура WP Sidebar Editor

## Структура

```
src/
  manifest.ts            один источник manifest.json для Chrome и Firefox (генерируется при сборке)
  background/index.ts    клик по иконке → открыть панель (sidePanel / sidebarAction)
  types/index.ts         общие типы: Field, Provider, EditorContext, Connection, BridgeData…
  lib/                   без DOM панели, тестируется изолированно
    storage.ts           типизированная обёртка над chrome.storage.local + «запись с TTL»
    wp-client.ts         buildRestUrl, транспорт через вкладку (executeScript), разбор ошибок WP
    token-client.ts      транспорт с Bearer-токеном, refresh (с дедупликацией), повтор при 401
    connections.ts       сохранённые подключения к сайтам
    cache.ts / drafts.ts кэш схем (15 мин) и черновики несохранённых правок (24 ч), ключи версионированы
    dates.ts             канонические форматы дат и конвертация в форматы ACF / WP / WooCommerce
    i18n.ts              строки интерфейса (en/ru), настройки, тема
  providers/             по одному файлу на источник данных (core, term-core, acf, woocommerce, yoast, term-yoast, front-page)
    registry.ts          явный упорядоченный список провайдеров
  sidebar/
    index.html, main.ts  точка входа панели: настройки, отслеживание вкладок
    state.ts             единый объект состояния панели
    context.ts           определение WP-страницы во вкладке, сборка EditorContext (live / connection)
    controller.ts        переключение между live-вкладкой и подключением
    layout.ts            шапка, экраны-заглушки, кнопка «Назад»
    banner.ts            баннер «найдена другая страница» и индикатор проверки
    dom.ts               мини-хелпер h() для построения DOM (только textContent, без innerHTML)
    views/               editor, connections, browser (поиск контента), settings
    fields/              render (Field[] → DOM), collect (DOM → значения), date, image, mask
wp-plugin/sidebar-editor-bridge/      плагин-мост для WordPress (см. раздел «Плагин-мост»)
wp-plugin/.wordpress-org/             скриншоты для страницы плагина на WordPress.org (в zip не попадают)
tests/                   Vitest (unit + jsdom), tests/e2e (Playwright), tests/php (классы моста без WP),
                         tests/integration (мост на настоящем WordPress)
scripts/                 zip-writer.mjs (ZIP на чистом Node), zip.mjs (расширение), zip-plugin.mjs (плагин)
composer.json            только dev: WordPress Coding Standards + PHPCompatibility (`composer lint`)
```

## Как всё связано

1. **Определение страницы.** Плагин-мост печатает `<script id="seb-bridge-data">` (JSON с REST-root, nonce,
   текущим объектом и списком активных плагинов) только для залогиненных редакторов. Панель читает его через
   `chrome.scripting.executeScript` (`context.ts → detectLiveContext`). Через REST это сделать нельзя: WordPress
   превращает cookie-запрос без nonce в анонимный, и получение nonce через REST замыкается само на себя.
2. **Два транспорта, один интерфейс.** `EditorContext.request()` возвращает одинаковый `RestResponse`:
   - *live*: `fetch` выполняется внутри страницы (cookie + `X-WP-Nonce`), см. `wp-client.ts → pageFetch`;
   - *connection*: `fetch` из самого расширения с `Authorization: Bearer` (`token-client.ts`). Работает без
     открытой вкладки. Пока вы на живой вкладке, `controller.ts → syncConnection` тихо выпускает/обновляет токены.
   Провайдерам всё равно, какой транспорт используется.
3. **Провайдеры** (`Provider` в `types`): `detect → load → getSchema → save(ctx, values, schema)`. Схема — это
   массив `Field` (id, label, type, value, …), из которого `fields/render.ts` строит форму. Третий аргумент
   `schema` в `save` — исходная (без черновика) схема секции. По ней провайдер понимает, что реально изменилось,
   и как конвертировать значение обратно.
4. **Форма.** У каждого редактируемого контрола есть `data-section/field/type`. По ним `fields/collect.ts`
   собирает значения, по ним же работает автосохранение черновиков (делегированный `input` на `#app`).
5. **Кэш и черновики.** Схема кэшируется после загрузки и после сохранения: перезагрузка страницы после Save
   не ходит в сеть. Черновики перекрывают значения схемы и удаляются после сохранения. В ключи входит
   `SCHEMA_VERSION`: если формат полей меняется, старые записи просто игнорируются.

## Даты

Внутри панели у каждого поля-даты одна каноническая строка, совпадающая с форматом нативного input:

| тип поля   | input                 | значение              |
|------------|-----------------------|-----------------------|
| `date`     | `type="date"`         | `2026-05-21`          |
| `datetime` | `type="datetime-local"` | `2026-05-21T19:00` (секунды только если не `:00`) |
| `time`     | `type="time"`         | `19:00`               |

Конвертация происходит только на краях, в провайдерах (`lib/dates.ts`):

- **ACF**: `date_picker` хранится как `Ymd`, `date_time_picker` как `Y-m-d H:i:s`, `time_picker` как `H:i:s`.
- **WP core** (`date` записи) и **WooCommerce** (`date_on_sale_from/to`): `YYYY-MM-DDTHH:MM:SS`, время сайта, без зоны.
- Часовые пояса нигде не пересчитываются: во всех этих местах WordPress хранит «настенное» время сайта.

**Почему раньше ломалось.** Мост отдавал значения ACF через `get_field_objects()` с форматированием
(`return_format`), например `21 Травня, 2026`. Панель показывала это как обычный текст, а при сохранении
`update_field()` записывал строку как есть, и поле даты портилось. Теперь:

- мост 0.7.0 отдаёт для полей-дат сырое значение в ISO (`raw: true`), а при сохранении сам нормализует любое
  ISO или «родное» значение ACF и **отказывается** записывать то, что не является датой (`skipped` в ответе);
- расширение отправляет уже готовый формат ACF, так что даже со старым мостом сохраняется правильно;
- если значение не удаётся разобрать (старый мост, нестандартные данные), поле показывается только для чтения
  с подсказкой обновить мост и в сохранение не попадает. Пустой календарь, который при Save затёр бы дату,
  не показывается никогда.

Дата публикации записи и даты распродажи WooCommerce отправляются только если их изменили. Повторная отправка
нетронутой даты у черновика «закрепила» бы его плавающую дату, а у WooCommerce дата окончания хранится как
`23:59:59`, поэтому там используется `datetime`, а не `date`.

## Что поменялось при переносе (кроме синтаксиса TS)

- `sidebar.js` (~1400 строк) разбит на модули: состояние, контекст, контроллер, экраны, поля.
- Провайдеры больше не регистрируются побочным эффектом импорта: в `providers/registry.ts` явный список.
- IMask подключается из npm, а не из `vendor/`.
- Найденные и исправленные баги:
  - post-провайдер Yoast срабатывал и на страницах терминов (две секции `yoast`), а также на главной
    со списком записей (запрос к `/wp/v2/undefined/undefined`); ACF на такой главной тоже. Теперь `detect`
    проверяет тип объекта;
  - в списке статусов не было `future`: у запланированной записи select показывал `publish`, и Save её публиковал;
  - ACF multi-select (значение-массив) сохранялся одним значением. Теперь такое поле только для чтения;
  - логин не откатывался на plain permalinks: WP-ответ 404 содержит JSON-сообщение без цифры «404».
    Теперь проверяется HTTP-статус (`HttpError`);
  - несколько параллельных запросов с просроченным токеном делали несколько refresh одновременно, а мост
    ротирует refresh-токен при каждом использовании, и все запросы, кроме первого, падали. Теперь refresh
    общий (`inflightRefresh`);
  - Ctrl+S на экране добавления подключения «сохранял» пустую форму и перезагружал вкладку;
  - **каждая открытая секция загружалась дважды**: Chromium шлёт событие `toggle` и для `<details>`, созданного уже
    открытым. На медленном сайте второй ответ приходил, когда пользователь уже начал печатать, и перерисовывал поля
    поверх введённого. Найдено e2e-тестом на настоящем WordPress, на быстром фейковом сервере не проявлялось;
  - **безопасность моста**: маршруты `/acf/<ref>` и `/term-seo/…` проверяли только `edit_posts`. Любой
    contributor мог читать и писать ACF-поля чужих и опубликованных записей, option-страниц и профилей
    пользователей. Теперь проверяется `edit_post` / `edit_term` для конкретного объекта, а ref вида `option`,
    `user_N` и т.п. отклоняется.

## Плагин-мост (Sidebar Editor Bridge 1.0.0)

```
sidebar-editor-bridge/
  sidebar-editor-bridge.php   заголовок плагина, константы, подключение классов, Plugin::boot()
  uninstall.php               удаляет настройки и user meta
  readme.txt                  формат WordPress.org
  languages/*.pot             строки для перевода (text domain sidebar-editor-bridge)
  includes/
    class-plugin.php          хуки и REST-маршруты, ссылка «Settings» в списке плагинов
    class-settings.php        опция sidebar_editor_bridge_settings (вкл/выкл подключений, сроки токенов), эпоха отзыва
    class-jwt.php             HS256, ключ из wp_salt('auth'); отвергает alg≠HS256
    class-tokens.php          выпуск/проверка пары токенов: iss (сайт), эпохи (сайт + пользователь), pwh (пароль)
    class-auth.php            Bearer → текущий пользователь, только для REST-запросов
    class-rate-limiter.php    5 неудачных логинов на IP+логин за 15 минут → 429
    class-permissions.php     edit_post / edit_term для конкретного объекта
    class-bridge-data.php     <script id="seb-bridge-data"> для редакторов (без списка capabilities)
    class-providers.php       какие интеграции активны (фильтр sidebar_editor_bridge_providers)
    class-acf-dates.php       даты ACF ↔ ISO (чистые функции)
    rest/                     auth, acf, term-seo, create-translation
    integrations/             Yoast (register_post_meta), WooCommerce (REST для атрибутов)
    admin/                    страница настроек, блок в профиле пользователя
```

Классы в пространстве имён `SidebarEditorBridge`, всё глобальное (константы, опции, user meta, transients, хуки)
с префиксом `sidebar_editor_bridge`. REST-пространство `sidebar-editor/v1` и id `seb-bridge-data` не менялись, так что
расширение работает с 1.0.0 без изменений.

**Что поменялось по сравнению с однофайловой 0.7.0:**

- **Токены.** Привязаны к сайту (`iss`): на мультисайте соли и пользователи общие, раньше токен одного сайта
  подходил к другому. Добавлен отзыв: «Sign out all extension sessions» в настройках (для всех) и галочка в профиле
  (для себя), и для access-токенов он действует сразу. `pwh` теперь HMAC от хэша пароля, а не обрезанный md5.
  Bearer принимается только на REST-запросах. Сроки жизни настраиваются, подключения можно выключить целиком.
  **После обновления сохранённые подключения один раз попросят войти заново** (другой формат токенов).
- **Логин** ограничен по числу попыток. `wp_authenticate()` по-прежнему запускает фильтры `authenticate`, так что
  плагины защиты входа продолжают работать.
- **ACF запись:** только существующие поля и только «плоских» типов (repeater, group и т.п. отклоняются), select/radio
  только из choices, email/url/число валидируются, текст проходит `wp_kses_post` для пользователей без
  `unfiltered_html`. В ответе есть `updated` / `skipped`.
- **Yoast:** meta регистрируется с `sanitize_callback` и проверкой `edit_post` конкретной записи; term SEO санитизируется.
- **Polylang:** проверяются язык и права на создание записей, повторный перевод на тот же язык даёт 409.
- **Bridge data** печатается через `wp_print_inline_script_tag` с `JSON_HEX_TAG`. Запись или термин попадают туда,
  только если пользователь может их редактировать. Список всех capabilities пользователя больше не выводится.

**Проверено:**

- WordPress Coding Standards и PHPCompatibility (PHP 7.4+) без замечаний.
- PHPCS-наборы Plugin Check (`plugin-check.ruleset.xml`, `plugin-review.xml`) без замечаний. Сам плагин Plugin Check
  целиком не запускался: для него нужен composer, а packagist в этой среде закрыт.
- Настоящий WordPress 7.0 + ACF 6.8.10 (SQLite):
  - `tests/integration` — 10 сценариев: даты, запрет на запись не-дат, права контрибьютора, refresh и подделка
    токена, лимит логинов, cookie + nonce, данные для панели;
  - `tests/e2e/real-wp.e2e.mjs` — расширение через собственную форму подключения меняет дату в календаре, значение
    проверяется в БД; выключение подключений и «sign out all» на странице настроек;
  - отдельно проверены отзыв по пользователю и по сайту, а также `uninstall.php`;
  - собранный zip установлен через `wp plugin install` и активирован.

## Сборка

Vite собирает два входа: `sidebar/index.html` (всё, что подключено из HTML, включая CSS) и
`background/index.ts` (фиксированное имя `background.js`, на него ссылается манифест). `manifest.json`
генерируется плагином в `vite.config.ts` из `src/manifest.ts`, версия берётся из `package.json`.
`--mode chrome|firefox` выбирает цель и папку `dist/<target>`. Минификация выключена: код удобнее отлаживать
в браузере, и AMO это предпочитает.

## Тесты

- `tests/*.test.ts` — Vitest + jsdom, `chrome.*` подменяется в `tests/setup.ts` (in-memory storage).
  Покрыто: разбор/конвертация дат, все провайдеры (схема и тела запросов), кэш/черновики/TTL, подключения,
  токены (refresh, 401-retry, дедупликация), рендер полей и сбор формы, контекст, манифест.
- `tests/e2e/smoke.e2e.mjs` — настоящий Chromium с собранным `dist/chrome` и фейковым WP REST. Путь: режим
  подключения → поиск → открытие записи → календари с правильными значениями → изменение и очистка → Save →
  проверка того, что ушло на сервер.
- `tests/php/run.php` — классы моста без WordPress (JWT, токены и их отзыв, настройки, права, лимит логинов, даты ACF).
- `tests/integration/bridge.integration.mjs` и `tests/e2e/real-wp.e2e.mjs` — мост и расширение на настоящем WordPress.
- `.github/workflows/ci.yml` — всё перечисленное на каждый push.

## Предложения по архитектуре (не реализовано)

По убыванию пользы:

1. **Отправлять только изменённые поля для всех провайдеров.** Сейчас так работают только даты. Базовая схема
   уже хранится в `state.sections[id].schema`, так что фильтр можно сделать один раз в `editor.save()` до вызова
   `provider.save`. Это уберёт перезапись чужих правок, сделанных в соседней вкладке или другим редактором.
2. **Оптимистическая блокировка.** Запоминать `modified_gmt` при загрузке и сравнивать перед сохранением.
   Если запись изменили, показывать «запись изменена с момента открытия» вместо молчаливой перезаписи.
3. **Один транспорт.** После `syncConnection` у панели всегда есть токен, а `executeScript` можно оставить только
   для чтения `#seb-bridge-data`. Это даст меньше движущихся частей, загрузку файлов без base64 через границу
   executeScript и одинаковое поведение live- и connection-режима.
4. **Редактирование сложных ACF-полей** (group / repeater, например блок «Про курс» в JSON). Нужен тип поля
   `group` с вложенными `Field[]` в рендерере и рекурсивные `acfFieldToSchema` / `acfValuesForSave`. Даты внутри
   групп при этом заработают автоматически.
5. **Нормализация схемы на стороне моста.** Тип поля, варианты и формат даты сейчас решаются в TS-провайдере,
   а сырые значения — в PHP. Если мост будет сразу отдавать `Field[]` (PHP знает реальный тип и настройки ACF),
   провайдер ACF станет тонким, а новые типы будут добавляться в одном месте.
6. **Токены в расширении.** Access-токен можно держать в `chrome.storage.session` (не переживает перезапуск
   браузера). Серверная часть (отзыв, привязка к сайту) уже сделана в мосте 1.0.0.
7. **Плагин-мост:** перенести интеграционные тесты на PHPUnit + `wp-env`, версионировать REST-пространство
   (`sidebar-editor/v2` при ломающих изменениях), показывать в панели сообщения 429 и `seb_connections_disabled`
   по-человечески.
8. **Подписи полей**: core-провайдеры отдают английские label. Стоит перевести их через `i18n.ts`
   (ключи по `field.id`).
9. **Firefox**: проверить вживую (sidebar, executeScript, выдачу host-permissions). Если доступ не выдан,
   показывать в панели кнопку `chrome.permissions.request`.
